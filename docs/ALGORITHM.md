# Алгоритм оптимизации

**Версия:** `v0.6.9 stable`

## Постановка

FieldRoute AI решает задачу класса **Vehicle Routing Problem with Time Windows (VRPTW)** с дополнительными ограничениями по квалификации инженера и типу транспорта.

Цель — построить допустимый дневной план для нескольких инженеров и распределить заявки с учетом временных окон, смен, длительности работ и дорожных перемещений.

## Конкурсный приоритет

Для конкурсной стратегии используется единая функция стоимости:

```text
min C = Σ Pj·uj + F·Σ yv + Σ dij·xij
```

где:

- `uj = 1`, если заявка `j` не назначена;
- `yv = 1`, если инженер `v` задействован;
- `xij = 1`, если маршрут содержит переход `i → j`;
- `dij` — дорожное расстояние перехода.

Фактические параметры конкурсного профиля:

```text
P обычной заявки = 100 000 000
P срочной заявки = 300 000 000
F за инженера    =   2 000 000
стоимость дуги   = дорожное расстояние в метрах
```

За счет доминирующих штрафов практический порядок приоритетов:

1. назначить максимально возможное число заявок;
2. задействовать минимально возможное число инженеров;
3. минимизировать суммарный пробег.

Это не отдельная многошаговая лексикографическая оптимизация, а одна функция стоимости, в которой штраф за потерю заявки существенно превышает стоимость подключения инженера, а стоимость подключения инженера существенно превышает типичную стоимость дополнительного дорожного плеча.

## Hard constraints

### Квалификация

Инженер должен обладать требуемым навыком.

Используемые категории:

- Локальные работы;
- Работы на подключение и дозаказы;
- Аварийные работы.

### Транспорт

Если у заявки задано требование к транспорту, тип транспорта инженера должен совпадать с ним.

Поддерживаются:

- Автомобиль;
- Пешеход;
- Велосипед;
- Общественный транспорт.

### Временное окно

Плановое начало выполнения заявки должно попадать в ее допустимое временное окно:

```text
window_start ≤ start ≤ window_end
```

### Рабочая смена

Выполнение работ должно завершиться до конца смены инженера:

```text
finish ≤ shift_end
```

Сверхурочное выполнение не используется как допустимое решение.

## Норматив времени

Для каждой категории используются нормативы организаторов.

Чтобы дорожное время не учитывалось дважды:

```text
service = technical + documents
travel  = max(routing_time, normative_road_time)
```

То есть сервисное время заявки включает техническую часть и документы, а дорожное плечо берется как максимум между фактическим временем по дорожной сети и нормативом дороги.

## Baseline

Baseline не выполняет глобальный поиск.

Алгоритм:

1. заявки рассматриваются во входном порядке;
2. для заявки перебираются инженеры в исходном порядке;
3. выбирается первый инженер, удовлетворяющий hard constraints;
4. заявка добавляется в конец его текущего маршрута;
5. если допустимого инженера нет, заявка остается неназначенной.

Порядок посещения соответствует порядку назначения.

## Поиск OR-Tools

Для построения начального решения используется:

```text
PATH_CHEAPEST_ARC
```

Для последующего улучшения:

```text
GUIDED_LOCAL_SEARCH
```

В стабильной конкурсной версии:

```text
основной solver = 10 seconds
replanning solver = 10 seconds
```

Если OR-Tools не возвращает решение, предусмотрен fallback на baseline.

## SLA

SLA является дополнительным KPI и не заменяет hard constraints.

В конкурсной стратегии штраф SLA в целевой функции отключен:

```text
sla_proxy_penalty = 0
```

В дополнительных стратегиях может использоваться soft upper bound для планового старта, эквивалентный стремлению завершить работу к концу желаемого окна.

Для встроенного датасета `sla_deadline` совпадает с концом окна заявки. Метрика SLA считается по факту завершения работы относительно этого дедлайна.

## Dynamic Replanning

При добавлении срочной заявки:

1. определяется текущее время;
2. завершенные и выполняемые работы фиксируются;
3. для каждого инженера определяется актуальная плановая стартовая позиция;
4. формируется набор оставшихся заявок;
5. добавляется срочная заявка;
6. остаток дня оптимизируется повторно;
7. новое распределение сравнивается с предыдущим.

Срочная демонстрационная заявка получает повышенный штраф за неназначение:

```text
300 000 000
```

## Plan Stability

Показатель рассчитывается как:

```text
Plan Stability =
1 - ChangedAssignments / ExistingFutureAssignments
```

где `ExistingFutureAssignments` — число ранее назначенных будущих заявок, которые входят в оставшийся горизонт планирования.

Чем выше показатель, тем меньшую часть будущих назначений пришлось изменить.

## Срочная заявка: ETA и SLA

Для срочной заявки:

```text
ETA = start_time - event_time
SLA margin = sla_deadline - start_time
```

В аварийном сценарии SLA трактуется как дедлайн реакции / прибытия: инженер должен прибыть и начать работу не позднее `sla_deadline`.

Длительность аварийных работ учитывается отдельно и не уменьшает запас SLA прибытия.

После события сравниваются изменения будущего плана, а не KPI полного дня с KPI остаточного горизонта.
