# Алгоритм оптимизации

## Постановка

FieldRoute AI решает задачу класса Vehicle Routing Problem with Time Windows с дополнительными ограничениями по квалификации и типу транспорта.

## Конкурсный приоритет

Результаты сравниваются лексикографически:

1. максимально назначить заявки;
2. минимизировать число задействованных инженеров;
3. минимизировать суммарный пробег.

В реализации это моделируется через:

- очень высокий penalty за неназначенную заявку;
- fixed cost активации инженера;
- дорожную стоимость дуг.

## Hard constraints

### Квалификация

Инженер должен обладать требуемым навыком.

Используемые категории:

- Локальные работы;
- Работы на подключение и дозаказы;
- Аварийные работы.

### Транспорт

При наличии требования заявки тип транспорта инженера обязан совпадать с ним.

Поддерживаются:

- Автомобиль;
- Пешеход;
- Велосипед;
- Общественный транспорт.

### Временное окно

Начало выполнения заявки должно находиться внутри допустимого окна.

### Рабочая смена

Маршрут и выполнение работы должны помещаться в рабочую смену. Сверхурочное выполнение не используется как допустимое решение.

## Норматив времени

Для каждой категории используется норматив организаторов.

Чтобы избежать двойного учета дороги:

```text
service = technical + documents
travel  = max(routing_time, normative_road_time)
```

## Baseline

Baseline не выполняет глобальный поиск.

Для каждой заявки во входном порядке выбирается первый допустимый инженер. Заявка добавляется в конец его текущего маршрута, если hard constraints выполняются.

## Search

OR-Tools использует routing solver и Guided Local Search.

В стабильной конкурсной версии лимит основного поиска:

```text
10 seconds
```

Он выбран после сравнительного тестирования более коротких лимитов: дополнительное время поиска давало улучшения по конкурсным KPI на части наборов.

## SLA proxy

SLA является дополнительным KPI.

Поскольку отдельный SLA deadline не представлен для всех заявок как независимое поле, proxy оценивает завершение работы относительно конца желаемого временного окна.

Он не заменяет обязательный hard constraint временного окна.

## Dynamic Replanning

При добавлении срочной заявки:

1. определяется текущее состояние рабочего дня;
2. завершенные и выполняемые работы фиксируются;
3. инженеры получают актуальные плановые стартовые позиции;
4. формируется остаток заявок;
5. добавляется срочная заявка;
6. остаток дня оптимизируется;
7. новое распределение сравнивается с предыдущим.

## Plan Stability

```text
Plan Stability =
1 - ChangedAssignments / ExistingFutureAssignments
```

Чем выше показатель, тем меньше действующий план пришлось изменить.


## Финальная настройка срочного перепланирования

Срочное перепланирование использует тот же лимит поиска OR-Tools — 10 секунд.

Для аварийной заявки:

```text
ETA = start_time - event_time
SLA margin = sla_deadline - start_time
```

То есть SLA аварийной заявки трактуется как SLA реакции/прибытия. Длительность аварийных работ
учитывается отдельно и не уменьшает запас SLA прибытия.

После события сравниваются изменения будущего плана, а не KPI полного дня с KPI остаточного горизонта.
