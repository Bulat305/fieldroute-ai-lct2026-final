# FieldRoute AI

**Интеллектуальный сервис планирования рабочих маршрутов для выездных инженеров**

Конкурсный прототип для задачи «Билайн Бизнес» / ЛЦТ 2026.

**Web demo:** Web demo: https://fieldroute-ai-lct2026-final.onrender.com/  
**Версия:** v0.6.9 stable  
**Основной solver:** Google OR-Tools, лимит поиска 10 секунд

## Что решает сервис

FieldRoute AI автоматизирует распределение выездных заявок между инженерами и построение маршрутов с учетом:

- квалификации инженера;
- типа транспорта;
- временного окна заявки;
- рабочей смены;
- нормативной длительности работ;
- дорожного времени;
- приоритета заявки.

Основной конкурсный порядок оптимизации:

1. назначить максимально возможное число заявок;
2. задействовать минимально возможное число инженеров;
3. минимизировать суммарный пробег.

SLA отображается как дополнительный KPI и не заменяет обязательные hard constraints.

## Основные возможности

- встроены три конкурсных набора данных: Восток, Юго-восток и Югоцентр;
- официальный baseline по правилам ТЗ;
- глобальная маршрутизация OR-Tools;
- дорожная матрица и геометрия через OSRM;
- интерактивная карта MapLibre;
- отдельный маршрут выбранной бригады;
- плановая позиция бригады на текущее время;
- Explainable Dispatching — «Объяснить выбор»;
- диагностика неназначенных заявок;
- срочное перепланирование и Plan Stability;
- трехшаговый Demo Mode;
- импорт собственных CSV/XLSX;
- шаблоны инженеров и заявок;
- fallback при недоступности routing-сервиса.

## Нормативы

В проект интегрированы нормативы, предоставленные организаторами:

| Вид работы | Дорога | Технические работы | Документы | Базовый норматив |
|---|---:|---:|---:|---:|
| Подключение клиентов Базовая | 20 мин | 60 мин | 10 мин | 90 мин |
| Аварий на ТКД | 20 мин | 80 мин | 0 мин | 100 мин |
| Дозаказ оборудования | 20 мин | 10 мин | 10 мин | 40 мин |
| Локальная заявка / ремонт у клиента | 20 мин | 30 мин | 0 мин | 50 мин |

Чтобы дорожное время не учитывалось дважды:

```text
service_time = technical_time + document_time
travel_time  = max(road_network_time, normative_road_time)
```

## Hard constraints

Назначение запрещено, если:

- у инженера отсутствует требуемая квалификация;
- тип транспорта не соответствует требованию заявки;
- начало работ невозможно выполнить в заданном временном окне;
- работы не помещаются в рабочую смену.

Сверхурочная работа не используется как допустимое решение.

## Baseline

Для сравнения используется последовательный базовый алгоритм:

1. заявки рассматриваются во входном порядке;
2. для заявки выбирается первый допустимый инженер;
3. маршрут формируется в порядке назначений;
4. глобальная оптимизация отсутствует.

В интерфейсе сравниваются baseline и оптимизированный план по числу назначенных заявок, числу задействованных инженеров и пробегу.

## Финальный hotfix перепланирования

В финальной версии:

- основной план: OR-Tools, 10 секунд;
- срочное перепланирование: OR-Tools, 10 секунд;
- ETA аварийной заявки — время до начала работ;
- SLA аварийной заявки трактуется как дедлайн реакции/прибытия;
- после аварии KPI остатка дня не сравниваются напрямую с full-day baseline;
- Plan Stability показывает масштаб изменения будущего плана.

## Demo Mode

`▶ Демо` проводит три последовательных шага:

1. **Базовый план по ТЗ** — исходные KPI и маршруты.
2. **Оптимизированный план** — результат OR-Tools с лимитом поиска 10 секунд.
3. **Срочная заявка** — оперативное перепланирование оставшейся части дня.

После перепланирования показываются ETA, изменения назначений и маршрутов, а также Plan Stability.

## Объяснимость

Кнопка `Объяснить выбор` показывает:

- выбранного инженера;
- соответствие навыку;
- тип транспорта;
- альтернативных кандидатов;
- расстояние и расчетное время;
- причины исключения кандидатов;
- примененный норматив.

Объяснение формируется детерминированно из ограничений и результата solver-а.

## Важные допущения прототипа

Предоставленные наборы не содержат полного набора всех производственных атрибутов, поэтому часть данных формируется детерминированными правилами. В частности:

- состав навыков/транспорта для сформированного roster инженеров;
- рабочая смена в демонстрационном roster;
- требования транспорта для части заявок;
- координаты заявок при отсутствии lat/lon.

Координаты встроенных заявок сейчас используют документированный `district-centroid-fallback`: район/город + стабильное смещение по адресу. Поэтому дорожная сеть реальная, но исходные географические точки являются приближенными.

Все такие допущения показаны во вкладке `Данные` и подробно описаны в `docs/DATASET_AND_ASSUMPTIONS.md`.

## Ограничения MVP

- нет GPS-телеметрии: «позиция бригады» является плановой;
- нет real-time traffic;
- публичный OSRM используется как внешний routing backend;
- координаты части исходных заявок приближенные;
- состояние пользовательского импорта хранится в памяти процесса;
- отсутствуют production RBAC и промышленная БД.

Это конкурсный прототип, а не промышленная FSM-платформа.
